本文将已有聊天规则转成可逐步核对的案例，重点观察点名、消息归属、轮次与上下文。所有问题、回答片段和事件均为人工构造，不是实际 API 响应，也不是测试通过的证据。当前静态原型尚不能执行这些业务案例。

## 阅读与核对口径

- 五组案例独立执行，各分支和顺序变体都从自己的前提重新开始，不继承上一组的调用数量或历史。
- 文中的“调用次数”仅指该案例观察期间发起的聊天生成请求，不包含预先准备的历史或连接测试。不能仅凭界面有几张回答卡片判断实际调用次数。
- “相同上下文”指发送时固定的相同可见历史与本次问题，保留发言者身份；两家供应商的请求格式可以不同，不要求原始请求逐字一致。
- 事件用自然语言描述，文本片段表示本次新到达的内容，不规定供应商原始流格式、通信消息字段、数据库结构或内部实现。
- 回答完成与用量完整程度分别判断。本文核对聊天行为，用量结算沿用 [Token 用量验收样例](token-usage-examples.md)，不以回答成功推断已获得完整 usage。

## 1. 单模型点名

**执行状态：未执行。**

**前提：** 新会话没有历史消息或运行中的调用；本次只选择 DeepSeek。

**用户操作与人工事件：**

1. 用户输入“请提出两条核对研究材料的问题。”并发送一次。
2. DeepSeek 先返回“材料来自哪里？”，再返回“发布日期是什么？”，随后正常完成。
3. 用户停留在会话中，不继续发送。

**预期展示：** 显示这条用户消息和带有 DeepSeek 身份的回答。回答随片段逐步出现，最终正文为“材料来自哪里？发布日期是什么？”，状态为完成。千问没有生成中状态或新增回答；回答结束后不自动开始下一轮。

**调用与上下文核对点：** DeepSeek 新增调用 **1** 次，千问 **0** 次。请求包含本次用户问题；单路文本只进入对应回答，显示完成不产生额外调用。

## 2. 双模型交错回答

**执行状态：未执行。**

**前提：** 会话已有一条用户历史消息“本次只讨论材料核验。”，没有运行中的调用；选择 DeepSeek 和千问。

**用户操作与人工事件：** 用户发送“请各提出两条核对问题。”，随后按以下顺序提供人工事件：

| 顺序 | 事件 |
| --- | --- |
| 1 | 千问返回“哪些是事实？” |
| 2 | DeepSeek 返回“材料来自哪里？” |
| 3 | 千问返回“哪些是推测？” |
| 4 | DeepSeek 返回“发布日期是什么？” |
| 5 | 千问正常完成 |
| 6 | DeepSeek 正常完成 |

**预期展示：** 两个回答区独立逐步更新。DeepSeek 最终为“材料来自哪里？发布日期是什么？”，千问最终为“哪些是事实？哪些是推测？”。千问先完成时，DeepSeek 仍保持自身进度；双方完成后各显示完成状态。

**调用与上下文核对点：** 两家各新增调用 **1** 次。两路输入都包含发送时的历史消息和本次问题，不包含本轮另一模型正在生成的回答。将事件 5、6 的完成顺序互换后独立核对，输入内容、文本归属和最终正文均不变；先完成的一路不触发另一轮请求。

## 3. 生成期间编辑下一条

**执行状态：未执行。**

**前提：** 新会话同时邀请两家回答“请提出材料核验问题。”；两路调用均已开始，尚未完成。

**用户操作与人工事件：**

1. 用户在输入区编辑下一条“请解释为什么要检查发布日期。”，尝试再次发送。
2. DeepSeek 正常完成，千问仍在生成；用户再次尝试发送草稿。
3. 千问正常完成；用户暂不发送。
4. 用户选择仅让千问回答，再主动发送这条草稿一次；千问返回“用来判断材料是否仍适用于当前讨论。”并正常完成。

**预期展示：** 步骤 1、2 中草稿可编辑，但不能开启下一轮，也不会作为已发送消息插入会话。步骤 3 中草稿仍待用户发送。步骤 4 才新增用户消息及千问的回答，先前两路内容保留。

**调用与上下文核对点：** 步骤 1 至 3 的调用数量始终为 DeepSeek **1** 次、千问 **1** 次；仅剩一路生成时同样不能开启下一轮。编辑草稿不改变已经发出的本轮输入。步骤 4 后本案例合计为 DeepSeek **1** 次、千问 **2** 次，新增调用来自用户这次主动发送。

## 4. 单路取消或失败

**执行状态：未执行。**

**前提：** 新会话同时邀请两家回答“请提出材料核验问题。”。DeepSeek 已显示片段“材料来自哪里？”，千问已显示片段“哪些是事实？”，双方都未正常完成。以下两个分支分别从此前提执行。

| 分支 | 用户操作与人工事件 | 预期展示 | 执行状态 |
| --- | --- | --- | --- |
| 取消 DeepSeek | 用户停止 DeepSeek，该路进入取消状态；本分支不再提供该路文本或完成事件。随后千问返回“哪些是推测？”并正常完成 | DeepSeek 保留“材料来自哪里？”，明确显示已取消、回答未完成；千问继续显示完整正文“哪些是事实？哪些是推测？”并完成 | 未执行 |
| DeepSeek 断流失败 | DeepSeek 在已有片段之后发生断流，进入失败状态；本分支不提供该路完成事件。随后千问返回“哪些是推测？”并正常完成 | DeepSeek 保留“材料来自哪里？”及失败状态，不伪装成完整回答；千问继续显示完整正文并完成 | 未执行 |

**调用与上下文核对点：** 每个分支中两家各调用 **1** 次，没有自动重发。DeepSeek 的取消或失败不清空千问内容、不停止千问，也不改变其已经发出的上下文。两个模型的文本和状态可以分别核对。

这里明确采用“先收到片段，再取消或失败”的顺序，不涉及取消与完成同时发生的裁决。取消展示不证明供应商没有继续产生消耗；完整、部分或未知用量的判断见 [单路失败或取消的 Token 案例](token-usage-examples.md#5-单路失败或取消)。

## 5. 用户发起下一轮

**执行状态：未执行。**

**前提：** 会话中已保存以下讨论，且当前没有运行中的调用：用户提出“请提出材料核验问题。”；DeepSeek 完成回答“材料来自哪里？”；千问完成回答“发布日期是什么？”。

**用户操作与人工事件：**

1. 用户查看已有回答，不发送消息。
2. 用户仅选择千问，发送“请结合前面的两条问题继续说明。”一次。
3. 千问返回“来源说明出处，日期说明时点。”并正常完成。

**预期展示：** 步骤 1 不新增生成或回答。步骤 2、3 新增一条用户追问和一条千问回答，原有讨论仍保留各自身份；DeepSeek 不自动加入，也不会因千问的新回答开始回复。

**调用与上下文核对点：** 本次观察期间仅千问新增调用 **1** 次，DeepSeek **0** 次。千问输入包含此前用户问题、两家已完成的回答和本次追问；原有回答保留模型作者身份，不被伪装成用户事实或系统指令。本轮千问的新输出不会自动触发下一轮。

**未完成历史分支（未执行）：** 独立重置前提，将先前 DeepSeek 回答改为已取消、仅保留“材料来自哪里？”的部分文本，其余条件相同。重复上述操作，DeepSeek 的部分文本仍可查看并保持未完成标识，不自动作为完整回答进入下一轮上下文；千问已完成的历史和本次追问正常参与。这一分支只核对既有边界，不新增如何编码未完成历史的方案。

## 如何用于七步学习

沿用 **需求 → 模块 → 数据 → 流程 → 并发与一致性 → 异常处理 → 扩展与验证**：

1. 从案例的用户操作与预期展示提炼需求和成功标准。
2. 先提出自己的模块分工与数据归属，解释怎样区分用户、模型、轮次和调用；本文不预先给出字段或模块实现。
3. 按人工事件梳理正常流程，再用交错返回、生成中编辑和局部失败检查并发与一致性、异常处理。
4. 实现后逐项比较实际结果，说明方案在哪些条件下成立，以及何时需要重新评估。

首个设计练习继续使用 [MVP 计划中的目标、约束和三个问题](mvp-plan.md#8-首个设计练习)。本文件提供验收输入与预期行为，不替代你的设计初稿。
