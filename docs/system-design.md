# Market Council 总体系统设计

更新日期：2026-11-13。状态：设计规划，尚未实现。

本文区分已经确定的可展示 MVP 与后续候选扩展。总体设想用于指导边界和取舍，不代表所有模块都会实现，也不构成完成时间承诺。

项目入口见 [README](../README.md)，近期任务、七步训练方式与验收流程见 [MVP 执行计划](mvp-plan.md)。

## 1. 产品目标与 MVP 边界

Market Council 是个人使用的多模型投研讨论 App。用户提供财经话题或文本材料，主持两个外部 API 模型的讨论，并在同一个 App 内查看 Token 消耗。

首版面向 macOS Apple Silicon，包含以下能力：

- 配置 DeepSeek 与千问的 API 凭据和模型名称，查看接入状态。
- 创建或打开会话，点名一个或两个模型回答，逐路显示流式文本及调用状态。
- 停止指定模型的生成，保留已经返回的内容，分别呈现各模型的成功或失败。
- 在 App 内查看当前会话与全部会话的输入、输出与总 Token，按模型显示占比，并能核对调用明细。
- 在本机保存聊天与用量记录，重启 App 后恢复查看。

MVP 的交付形态是可以从 Finder 启动的独立 App。API 设置、聊天和 Token 看板均在 App 内完成，不能仅以命令行脚本或浏览器页面代替验收。

本地模型、自动圆桌、联网采集、定时日报、行情查询、决策卡和金额分析属于候选扩展。首版讨论依据用户提供的内容，不暗示已经具备实时财经数据。

## 2. 总体分层

| 层次 | 选型 | 职责 |
| --- | --- | --- |
| 桌面界面 | React + TypeScript | API 配置表单、会话与消息、逐路状态、Token 看板 |
| 桌面容器 | Electron | 窗口、系统能力、受控 IPC、Python worker 生命周期 |
| 本地业务 | Python worker + Pydantic | 会话上下文、调用调度、供应商适配、用量归一化和持久化 |
| 进程通信 | UTF-8 JSON Lines | 传递请求、文本增量、状态、用量和错误；日志使用 stderr |
| 数据存储 | SQLite | 保存会话、消息、调用与用量；Python 为唯一业务写入方 |
| 凭据存储 | macOS Keychain | 保存 API Key；普通配置与业务记录只引用凭据 |
| 分发 | Electron Forge + PyInstaller | 打包桌面资源及 Python worker 的完整运行目录 |

交互路径为：React → preload 受控接口 → Electron 主进程 → Python worker → 供应商 API；结果按相反方向回到界面。

界面不直接拼装供应商请求或写数据库。Python 业务层决定本轮调用哪些模型、发送哪些历史消息，以及何时保存消息和用量。Electron 负责启动、关闭和观察 worker，避免业务规则散落在两个语言层。

聊天与用量留在本机；调用外部 API 时，选定的上下文会发送给对应供应商。未来的自建日报服务不作为聊天数据的存储端。

## 3. 模型适配边界

MVP 分别实现 DeepSeek 官方 Chat Completions 与千问 DashScope 原生协议适配器，不把所有服务当作仅需更换地址的同一种接口。

| 适配层输入 | 对上层输出 |
| --- | --- |
| 调用 ID、模型配置、固定的上下文与生成参数 | 文本增量、调用完成状态、用量快照、供应商请求标识或错误 |

供应商的消息格式、增量或累计文本形式、结束信号和 usage 字段在适配器内处理。会话界面只消费统一事件，避免在 UI 中判断两家的协议差异。

供应商模型名称按用户账户可用情况配置。适配器保留原始 usage 字段及其来源，再生成看板需要的标准字段；不预设两家提供完全相同的细分统计。

## 4. 主持式讨论流程

1. 用户输入消息，并选择 DeepSeek、千问或两者参与。
2. 业务层保存用户消息，为本轮固定上下文，分别登记每个模型的独立调用。
3. 选中的适配器发起请求，逐路产生文本和状态事件；界面将内容放入对应模型的消息区域。
4. 收到终态后保存该路消息、调用结果和可获得的用量；任一路失败不抹去另一模型的回答。
5. 用户查看本轮结果与 Token 明细，再点名模型追问，进入下一轮。

同一会话一次运行一轮。需要重新发起时先结束或取消当前各路调用；模型回答不会自动触发新一轮请求。

同轮参与者使用同一份已保存历史和本轮用户消息。本轮新生成的回答不进入另一模型正在执行的请求，因此谁先返回不会改变同轮输入。后续轮次可看到此前已完成的讨论内容；模型发言保留作者标识，不伪装成用户事实或系统指令。

MVP 不静默裁剪历史。某家模型无法接受当前上下文时明确显示该路失败，由用户调整输入或开启新会话；不能把不同的截断历史当作同条件回答比较。

## 5. 并发、取消与异常

- 两个外部 API 调用独立执行并采用有界并发；每一路有独立的调用 ID、输出、用量和终态。
- 用户可以逐路取消。取消后保留已接收文本并标明未完成，不将其当作正常完整回答。
- 某一路鉴权失败、限流、超时或断流时，只更新该路状态，另一模型继续处理。
- 事件按调用归属处理，晚到的事件不能写入其他轮次，也不能把已确定的终态退回生成中。
- 结果未知的付费调用不自动重发；用户重新发起会创建新的调用记录。恢复展示已有记录不应再次调用模型。
- worker 或 App 中断后，未完成调用恢复为中断或待核对状态，不显示成成功。关闭 App 时回收相关进程与连接。

数据库是聊天和看板的事实来源。持久化成功后再把对应记录视为已保存；UI 的生成动画或停止状态不能替代数据库中的调用结果。

## 6. Token 看板与结算原则

看板提供按模型的输入/输出分布与占比、当前会话和全部会话汇总，以及逐调用明细。实际发起生成请求的连接测试另列，不混入聊天会话合计。首版监控的是 Token 用量，不把尚未实现的价格计算显示成真实费用。

| 信息 | 处理方式 |
| --- | --- |
| 生成中的用量 | 有供应商累计 usage 时显示最新有效快照；尚未提供时显示待返回 |
| 已完成调用 | 使用供应商最终 usage 结算，并关联到对应调用和模型 |
| 缺失或不完整用量 | 标明未知或部分已知，不补零，不伪造精确 Token 数 |
| 缓存、推理等细分字段 | 按供应商定义保存；已经包含于输入或输出总量的部分不再次相加 |
| 总 Token | 优先使用供应商总量；仅在输入输出完整且口径允许时由两者计算 |

同一调用多次收到累计快照时，使用最新有效快照替换旧值，不能逐块累加。相同结果或结束事件重复到达时，只更新同一条调用记录，不追加第二笔消耗。

看板合计和占比从已结算的调用记录计算，部分用量与未知调用另列，不混入已结算合计；没有已结算用量时显示空状态。最终结算后，消息明细、按模型汇总与会话汇总需要一致。不同模型的 Token 数用于观察消耗，不直接作为回答质量评分。

流中断时可能已经发生供应商侧消耗。缺少最终 usage 的调用保持未知或部分已知，保留原始快照和状态，供后续核对。

## 7. 数据与配置归属

本机需要保存会话、带作者的消息、讨论轮次、模型配置引用、逐调用状态、用量快照与最终用量。字段细化和具体数据库结构在 MVP 设计练习中确定，本文不提前规定 SQL。

API Key 存入 Keychain，不写入聊天、普通数据库字段、日志或 Git。配置表单保存后仅展示必要的状态与脱敏信息；后端读取凭据完成请求。

数据库位于应用的用户数据目录，安装包不作为运行时写入位置。用户卸载或迁移应用时，聊天数据与凭据的处理需要明确说明；当前文档不声称已具备备份或跨设备同步能力。

## 8. 候选扩展与触发条件

| 候选能力 | 何时考虑 | 对现有边界的影响 |
| --- | --- | --- |
| OpenAI 原生 API | 两家调用、状态及用量链路稳定后，确有模型比较需求 | 新增适配器，不把供应商判断散入 UI |
| Ollama 本地模型 | 希望体验本机推理，并具备可用模型与硬件 | 新增本地执行入口；本地用量与 API 消耗分开说明 |
| 自动圆桌与独立比较 | 主持模式已被实际使用，用户明确需要更多讨论方式 | 增加轮次、上下文可见性、停止条件和调用预算设计 |
| 云端定时日报 | 需要电脑关闭时仍采集资料并生成报告 | 引入独立采集、调度、报告与用量服务 |
| 行情与材料采集 | 讨论需要可追溯的外部证据 | 标明来源、发布时间、采集时间及行情时点，美股数据优先 |
| 决策卡 | 需要保存并复盘投资假设与入场观察条件 | 区分来源事实、模型判断和用户确认的决策 |
| 费用分析 | Token 统计可靠且确需金额报表 | 加入供应商价格快照、币种与 Decimal 计算 |

如果未来实施云端日报，服务器只负责配置范围内的采集、报告生成及其 usage，不接收本机聊天。桌面单向拉取日报及用量，以稳定的来源和调用标识去重；重复下载不得重复统计消耗。

云端报告调用服务器上配置的 API 模型，因此 Mac 离线时仍可执行。桌面与云端凭据分别配置；Ollama 不承担依赖离线 Mac 的云端定时任务。上述服务仍为设想，本次不部署或启用。

## 9. 验证重点与官方参考

MVP 验证围绕独立 App 启动、两路真实流式回复、同轮固定上下文、逐路取消或失败、重复事件去重、用量缺失和重启恢复展开。具体展示步骤见 [MVP 执行计划](mvp-plan.md)，规划状态只有在相应证据产生后才能更新。

- [Electron 文档](https://www.electronjs.org/docs/latest/)：桌面运行环境与进程职责。
- [DeepSeek Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/)：官方请求、流式响应与用量协议。
- [千问流式输出](https://www.alibabacloud.com/help/zh/model-studio/stream)：DashScope 的增量与累计输出方式，以及 Token 用量。
- [SQLite 适用场景](https://www.sqlite.org/whentouse.html)：本地应用数据存储的选择依据。
- [Ollama 用量说明](https://docs.ollama.com/api/usage)：未来本地模型接入时可参考的 Token 与耗时指标。
