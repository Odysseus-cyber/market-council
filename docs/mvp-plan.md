## 1. 交付目标与边界

交付一个可从 Finder 启动的 macOS Apple Silicon `.app`。你在同一个 App 内完成模型配置、与 DeepSeek 和千问聊天、查看 Token 消耗，以及重启后浏览历史记录。常规使用不依赖终端、开发目录或另行启动的 Python 服务。

这次 MVP 的完成条件包含两个外部 API 模型。先接通一个模型只是开发过程中的可演示步骤。

本版只接收文本消息，财经材料通过粘贴进入讨论。更多供应商、本地模型、云端日报、自动讨论、行情采集、文件解析、联网检索、决策卡、费用换算和导出均为候选扩展，不属于本次验收。

## 2. App 内的使用流程

### 模型设置

在设置页面分别填写 API Key 与模型名称，为千问选择与凭据匹配的地域配置，测试连接并保存。可选模型以各自账号能够调用的模型为准，文档不锁定会变化的模型别名。

密钥保存在 macOS Keychain，SQLite 只保存凭据引用及普通配置。若连接测试实际发起了生成请求，同样记录其调用用量，并标识为连接测试，避免混入某个讨论会话。

### 聊天

创建或打开本地会话，输入文本，选择 DeepSeek、千问或两者，然后发送。每个模型有独立的回答区、生成状态和停止操作；你可以停止一路或全部生成。回答完成后继续发送下一轮消息。

同一会话只运行一轮。正在生成时可以编辑下一条输入，但需等待本轮结束或停止后再发送。不会因模型发言自动启动另一轮。

同时邀请两家时，固定发送时的历史消息与本次输入。每条历史消息保留发言者标识；适配器按供应商协议表达相同的可见上下文。两家在本轮内不读取对方尚未完成的输出，返回先后不改变输入。

部分或失败的回答可以保留展示并明确状态，但不自动作为完整回答加入下一轮历史。模型名称、调用状态和正文在界面上可区分。

### Token 看板

看板与聊天、设置同属 App。支持当前会话与全部会话两个范围，展示每个模型的输入、输出、总 Token、占比及调用明细。连接测试调用另列，不计入聊天会话合计。

已结算调用构成汇总与占比的基础；部分用量和未知调用单独展示数量及状态。没有已结算用量时显示空状态，不绘制虚假的占比。用量来自各模型接口，不以文字字数或流式片段数代替 Token 数。

## 3. 模块、数据与接口边界

| 部分 | 负责的内容 |
| --- | --- |
| React 界面 | 聊天、设置、Token 看板，以及各路调用状态 |
| Electron 主进程与 preload | 桌面能力、受控 IPC、Python worker 启停与事件转发 |
| Python 业务层 | 会话历史、轮次快照、调用调度、供应商适配、凭据访问、SQLite 读写与统计 |
| 供应商适配器 | DeepSeek Chat Completions、千问 DashScope 的请求转换、文本流和 usage 处理 |

Electron 与一个常驻 Python worker 通过 UTF-8 JSON Lines 通信。请求包含请求标识、操作与参数；长请求先登记调用，再发送文本增量、状态、用量和错误事件。stdout 用于协议，stderr 用于日志，不通过日志输出密钥。

最少需要区分以下数据对象，具体字段与迁移在设计练习和实现中逐步确定：

| 对象 | 需要区分的事实 |
| --- | --- |
| 会话与消息 | 会话归属、消息顺序、发言者、正文和完成状态 |
| 轮次 | 用户本次输入、受邀模型、固定上下文和本轮状态 |
| 模型配置 | 供应商、模型名称、地域和凭据引用 |
| 模型调用 | 每一次实际请求的独立标识、供应商请求 ID、状态、开始与结束时间 |
| 用量记录 | 调用归属、归一化 Token、原始 usage、统计完整程度 |

Python 是业务数据库的唯一写入方。数据库放在 App 的用户数据目录，不写入安装包。消息与用量以调用标识关联，不能只依赖界面显示顺序关联模型结果。

## 4. 并发、一致性与异常

### 两路回答独立推进

一轮最多调度两家供应商，各自拥有调用 ID、状态与输出。单路鉴权失败、超时或取消不清空另一模型的回答，也不重发已经成功的调用。

取消是对当前调用的请求，不意味着供应商一定没有继续生成或产生用量。界面停止状态和用量完整程度分别记录；已经收到的文本可以保留。

### 用量归一化与结算

- 统一表达输入、输出和总 Token，并保存原始 usage，便于按供应商口径核对。
- 累计用量字段取最新有效快照，不把每个流式片段中的累计值相加。
- 只有收到完整统计才标为已结算；部分统计保留为部分，未收到统计保留为未知。
- 缓存或其他细分字段只作为细分信息保存，不再次加到已包含它们的输入、输出或总量中。
- 同一调用的重复事件、重复完成通知只更新同一条用量记录；重新发起的请求使用新调用 ID。
- 汇总直接从已保存的调用用量计算，重启和重新打开看板不重复累计。

DeepSeek 的流式调用在末尾返回完整 usage；千问的流式协议与用量字段由其适配器分别处理。[DeepSeek 官方接口](https://api-docs.deepseek.com/api/create-chat-completion/)、[千问流式输出](https://www.alibabacloud.com/help/zh/model-studio/stream)

### 失败与恢复

失败或结果不明的生成请求不自动重发，并检查 SDK 默认重试行为。手动重试仅重试选定的模型，创建新调用，旧记录继续保留。网络中断时，不把缺失 usage 写成零。

应用异常退出后，重新启动时将遗留的运行中调用标记为中断，恢复已保存的消息与用量；不声称恢复了供应商侧的生成，也不自动重新调用。关闭 App 时处理 worker 的退出。

## 5. 四步实现顺序

| 步骤 | 实现内容 | 可演示成果与学习重点 |
| --- | --- | --- |
| 1. App 骨架与单模型 | 建立 Electron/React 与 Python worker，接通 DeepSeek 设置、流式回复、SQLite 保存；打包完整 Python 运行目录 | 在 App 内完成单模型对话，重启后可查看记录；理解用户目标、模块职责和消息何时算完成 |
| 2. 两模型讨论 | 接入千问原生接口，加入点名、固定轮次上下文、两路输出与逐路取消 | 两家同时回答同一条消息，单路失败不影响另一家；理解消息顺序、并发与局部失败 |
| 3. Token 看板 | 归一化两家 usage，实现明细、当前会话与全部会话统计、模型占比 | 从调用明细核对图表；理解累计快照、未知状态和重复事件处理 |
| 4. 完整展示验收 | 完成设置、聊天、看板串联，检查独立安装包、凭据读取和重启恢复 | 从 Finder 打开 App 完成整段演示；用实际结果说明设计是否成立 |

最小打包验证放在步骤 1；步骤 4 验证完整体验。worker 的完整 onedir 运行目录随 App 分发，并由 Electron 通过实际资源路径启动。[Electron ASAR 限制](https://www.electronjs.org/docs/latest/tutorial/asar-archives)、[PyInstaller 打包说明](https://pyinstaller.org/en/stable/operating-mode.html)

## 6. 展示与验收

### 展示脚本

1. 从 Finder 启动 `.app`，在设置页配置两家服务并测试连接。
2. 创建会话，粘贴一段带来源说明的财经文本并提问，同时邀请两家回答。
3. 观察两路流式回答，再点名其中一家继续追问；另演示停止一路生成。
4. 打开 Token 看板，核对模型分布、会话合计和对应调用明细。
5. 关闭并重新打开 App，确认历史消息、调用状态和已结算用量仍在。

### 关键验收场景

| 场景 | 预期结果 |
| --- | --- |
| 真实双模型聊天 | 两家 API 各完成至少一次真实请求，发言身份和上下文对应正确 |
| 同轮上下文 | 不同返回顺序不改变两家本轮输入；回答不自动触发额外调用 |
| 单路错误或取消 | 另一模型可以继续完成，已有正文不会被清空 |
| 累计 usage 与重复事件 | 重复快照或完成事件不扩大统计，输入输出明细与汇总口径一致 |
| 断流与用量缺失 | 部分或未知状态可见，不伪造零消耗或完整统计 |
| 手动重试 | 新请求单独记账，旧失败记录仍可追溯 |
| 本地恢复 | 重启后能看到历史与用量，中断任务不自动产生新的付费请求 |
| 看板范围 | 当前会话、全部会话、连接测试之间有明确归属，空数据状态正确 |
| 独立 App | 打包产物包含必要 Python 运行资源，正常使用不依赖终端或开发目录 |

业务测试优先验证调用状态与用量归一化；界面测试覆盖点名、分路状态及看板汇总。日常测试使用固定响应样例，真实 API 请求仅用于显式的接入与展示验收。没有执行过的测试与演示不得标为通过。

## 7. 七步学习方式

每个小功能都走一遍：**需求 → 模块 → 数据 → 流程 → 并发与一致性 → 异常处理 → 扩展与验证**。它是每个功能的推导顺序，与上面的四个交付步骤配合使用。

默认“你先设计，我追问评审”：助手给目标、已有约束和最多三个引导问题，你先用文字、草图或伪代码表达方案。助手先指出成立的部分，再针对缺口追问，每轮不超过三个问题；提示从场景、概念到局部示例逐步展开。你明确要求示范或直接实现时可以切换方式。

每个功能用一页以内的设计卡即可，不为七步分别写文件：

```markdown
功能：<本次小目标>；状态：待设计 / 实现中 / 待验证 / 已完成
1. 需求：<场景、成功标准、本次边界>
2. 模块：<职责与输入输出>
3. 数据：<必要数据、归属与必须保持的规则>
4. 流程：<正常步骤与成功时点>
5. 并发与一致性：<相关竞争场景；不涉及则说明原因>
6. 异常处理：<失败状态与恢复方式>
7. 扩展与验证：<验收例子、必要测试与重新评估条件>
证据与复盘：<实际结果、一种备选做法及当前取舍>
```

功能完成时同时检查：有可演示的功能证据；你能解释模块与数据归属；你能说明一种备选做法及何时值得重新考虑。分析深度随问题复杂度调整，不为填模板增加无关机制或测试。

## 8. 首个设计练习

### 目标

在 App 内向 DeepSeek 发送一条文本消息，看到逐步生成的回答，并在重启后查看回答与用量状态。

### 已有约束

- macOS Apple Silicon 桌面 App，Electron/React + Python worker，使用 JSON Lines 通信。
- Python 统一管理业务数据并写入本地 SQLite，API Key 存 macOS Keychain。
- 本练习先处理一家外部 API；两家模型与完整 Token 看板仍是最终 MVP 的验收内容。

### 先回答三个问题

1. 从用户角度，怎样判断这次聊天已经成功，重启后又应该看到什么？
2. 这个功能需要哪些模块参与，它们分别负责什么、互相传递什么？
3. 哪些数据必须持久保存，哪些可以临时保留，哪些状态现在还无法确定？
