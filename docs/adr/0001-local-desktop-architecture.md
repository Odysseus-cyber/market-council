# ADR 0001：本地桌面架构的选择与取舍

记录日期：2026-11-16。

状态：**架构方向已采纳，分阶段实施。** Electron/React 静态原型已落地；Python worker、业务通信、业务存储、凭据管理及独立打包尚未实现。本记录补记已有技术路线的理由，不代表本日新增了上述能力。

## 背景与约束

Market Council 面向个人投研讨论，由个人持续开发。开发者已有 Python 基础，偏好 Web 界面的表达方式，希望通过项目练习模块边界、数据归属、并发一致性与异常恢复。

首个 MVP 面向 macOS Apple Silicon：在一个 App 中与 DeepSeek、千问聊天，查看 Token 用量，并在本机保留记录。首版不需要部署自建云服务器；调用外部模型时，选定的上下文仍会发送给对应供应商。本地保存不等于模型调用离线完成。

当前能够运行的是使用固定演示数据的静态桌面原型。真实聊天与独立 `.app` 交付仍是目标，不能用界面运行结果证明业务通信、持久化或打包已经成立。

## 备选方案

| 方案 | 对本项目的价值 | 需要接受的代价 | 当前判断 |
| --- | --- | --- | --- |
| Electron + React/TypeScript + Python worker | 保留 Web 界面；让已有 Python 基础用于上下文、供应商适配和用量业务，也能练习清晰的进程职责 | 同时维护两套语言与工具链，处理跨进程通信、worker 生命周期和分发 | 沿用已选路线；Python 的价值仍需用实际开发与维护结果检验 |
| Electron + React/TypeScript，业务也使用 TypeScript | 界面与业务可使用同一语言，减少 Python 运行环境和两种语言之间的协议维护 | 业务逻辑需在 TypeScript/Node.js 中实现，已有 Python 经验不能直接用于这部分代码 | 是可行备选；如果 Python 没有带来足够收益，应重新考虑 |
| Python GUI | 界面与业务都可以围绕 Python 组织，减少跨语言协调 | 需要学习并使用相应 GUI 工具构建聊天、设置与图表，界面实现方式会偏离当前 Web 路线 | 当前优先保持 Web 界面方向；不据此断言 Python GUI 无法满足需求 |

**接入 AI API 并不要求使用 Python。** 这里选择 Python，是结合个人基础、业务开发方式与学习目标的项目取舍，不是供应商接口的技术要求。当前没有三种方案的性能、内存或包体积对比测量，因此不作优劣结论。

## 已采纳的职责与边界

| 决策 | 本项目的理由与边界 |
| --- | --- |
| Electron/React 负责桌面与界面 | React 表达聊天、设置和看板；Electron 管理窗口、受控 IPC 与 worker 生命周期。计划通过 preload 提供有限能力，不让界面直接处理供应商请求、数据库或凭据。当前原型尚无业务 preload 接口 |
| Python worker 负责业务 | 将上下文组织、供应商适配、调用状态、用量归一化和持久化归到同一业务层，避免在两种语言中重复维护规则 |
| Electron 与 worker 使用 UTF-8 JSON Lines | 当前只有桌面主进程与本地 worker 需要通信，先采用标准输入/输出连接，无需维护本地 HTTP 服务。stdout 用于协议，stderr 用于日志；这不免除请求关联、分段读取和错误处理的工作 |
| SQLite 保存本机业务数据，Python 是唯一业务写入方 | 适配单机记录与查询的当前目标，并明确写入责任。唯一写入方是本项目的组织选择，仍需设计事务和任务间的写入顺序，不能据此认为一致性已自动解决 |
| API Key 计划存入 macOS Keychain | 凭据与普通配置、聊天及用量分开管理；数据库只保存凭据引用。当前设置控件禁用，尚未接受或保存真实密钥 |
| Electron Forge + PyInstaller onedir 用于未来分发 | 沿用现有 Forge 工程，计划将 Python worker 的完整运行目录随 App 分发。当前仅验证了开发模式，Python 打包、资源定位与独立启动仍需在步骤 1 中验证 |

React 到 Electron 的受控 IPC，以及 Electron 到 Python 的 JSON Lines，是两段不同的通信边界。本记录解释它们存在的原因，不新增请求字段、消息类型或数据库结构；具体接口随功能设计与验证逐步确定。

## 接受的代价

- **两套语言与工具链**：前端与 Python 各自需要依赖、版本管理和检查；跨层修改可能同时影响两侧，不能假设类型会自动同步。
- **请求关联与流式处理**：需要把增量、状态和用量归到正确调用，处理分段读取、重复事件及晚到结果。JSON Lines 只是通信表达方式，不自动提供这些业务保证。
- **worker 生命周期**：需要处理启动失败、退出、超时与 App 关闭，避免界面永久等待或残留业务进程。
- **错误定位**：需要区分界面、Electron、worker 和供应商侧的问题，并让日志与协议互不干扰；不能把收到界面事件等同于持久化成功。
- **打包维护**：需要验证 Python 依赖收集、运行资源路径、目标平台与进程启动。当前开发环境能够运行 Electron，并不能证明用户脱离终端也能运行完整 App。

这些是后续实施要承担的工作，不是当前原型已经具备的机制。学习价值需要与维护成本一起衡量；不会仅为演示复杂架构而增加业务不需要的层次。

## 重新评估条件

| 出现的实际需求或证据 | 重新评估方向 |
| --- | --- |
| 多个独立客户端需要访问同一个业务服务，或需要远程访问 | 评估 HTTP 等服务接口，重新明确服务生命周期与访问边界；桌面内增加页面本身不是触发条件 |
| 需要跨设备并发写入同一份业务数据 | 评估服务端数据库及服务端写入责任，不把直接共享本地数据库文件当作既定同步方案 |
| Python 未带来足够的开发收益，而通信、依赖或打包维护持续成为主要负担 | 评估将业务统一到 TypeScript；依据实际功能与维护记录判断，不预设迁移一定更优 |
| 独立打包验证暴露出当前分发方式难以承担的限制 | 重新评估 worker 的打包与启动方式，再决定是否需要调整更大的架构边界 |

未来云端财经日报仍是候选扩展。按照现有设想，云端负责采集、生成报告及其用量，桌面拉取结果；这本身不要求把本机聊天迁往云端，也不自动触发对本地 worker 或 SQLite 的替换。以上条件用于决定何时讨论调整，不构成新增功能承诺。

## 技术事实与项目判断的依据

| 官方资料说明的事实 | 本项目据此作出的选择 |
| --- | --- |
| Electron 区分主进程与渲染进程，preload 可通过受控方式向页面提供能力。[Electron 进程模型](https://www.electronjs.org/docs/latest/tutorial/process-model) | 选择 React 表达界面、主进程管理桌面与 worker；Electron 文档并不要求使用 Python |
| SQLite 官方说明了本地应用存储的适用性，以及多台设备经网络直接访问同一数据库时需要考虑的限制。[SQLite 适用场景](https://www.sqlite.org/whentouse.html) | 当前采用本地 SQLite，并让 Python 统一写入；这是结合当前单机范围的取舍，不是对未来所有数据需求的保证 |
| PyInstaller 会收集解释器及所需文件，可生成单目录产物；输出与构建操作系统和 Python 环境有关。[PyInstaller 工作方式](https://www.pyinstaller.org/en/stable/operating-mode.html) | 计划使用 onedir 分发 worker，并尽早验证独立运行；尚无本项目的 Python 打包成功证据 |

此 ADR 与现有七步学习主线配合使用：在功能设计中检验模块、数据与异常边界，再用运行结果决定上述取舍是否成立。首个设计练习与业务验收状态保持原样，不以记录了决策代替实现或验证。
